Составлен 2026-11-04. Код этим планом не менялся. Начинать только после «да» пользователя.

  `ModelLibrary.swift:278` (20), `ImportRunner.swift:127` (19), `Options.swift:166` (18, это длинный

## Главное правило плана

Генерация — самое ценное, её нельзя сломать молча. Поэтому до первого изменения кода снимаем **эталонные
картинки**: несколько генераций с зафиксированным сидом, промптом и настройками (обычная картинка, правка
с маской, видео на пару секунд). После каждого куска те же настройки должны дать ту же картинку. Файлы
сравнивает скрипт, экран никто не трогает. Если движок на одном сиде не повторяется точь-в-точь, сравниваем
по близости и это пишем в отчёте.

## Шаг А. Тестовая цель, которая не тянет движок

Решение по форме: рядом с исходниками новая небольшая папка `app/Core` с собственным `Package.swift` и
без зависимостей. `swift test` в ней идёт секунды. `build.sh` копирует файлы `Core` в приложение тем же
способом, каким уже копирует `Storage.swift` и другие общие файлы в LilArtGen, поэтому приложение
собирается как раньше.

Что переезжает в `Core` (сначала файлы, которым уже не нужны ни движок, ни окно):
`ScaledCheckpoint`, `Storage`, `VideoOptions` (в нём `NoteSettings`), `PromptAssist`.
Потом вытаскиваем чистые куски из смешанных файлов:
- `RegionLayout` из `Regions.swift` (как рамки превращаются в текст запроса);
- разбор метаданных PNG и форматов A1111/ComfyUI из `SettingsImport.swift` (без привязки к семплеру движка);
- глоссарий и `keepingTerms` из `Translator.swift`, `pictureNumbers` из `Studio.swift`;
- разбор каталога и `classify` из `ModelLibrary.swift`, `importPlan`, `filesToMove`.

Файлы с NNC (`ModelParts`, `WeightCompressor`, `TensorImage`) пока не трогаем: NNC компилирует тяжёлую
библиотеку, это отдельный шаг позже, с предупреждением.

Тесты пишем **до** переноса каждого куска и сначала смотрим, как они падают. Сначала то, что уже ломалось:
1. Shift из заметки каталога (`NoteSettings`): 16 для FLUX.3, число «1» не путать с «16».
2. Перевод подсказок: слово «bra» не теряется, «картинка 2» превращается в «image 2».
3. Рамки зон: порядок `[y1, x1, y2, x2]`, шкала 0–1000, правка с `<ref_image_0>`.
4. Разбор настроек из PNG и Civitai: кодировка UTF-8, вложенная `meta.meta`.
5. Определение модели по имени файла (`classify`) и план переноса на внешний диск.
6. Масштаб fp8-весов (`ScaledCheckpoint`) на маленьком искусственном наборе чисел.

Проверки качества для `Core`: SwiftLint, покрытие через `swift test --enable-code-coverage`, CRAP по формуле
`CC² × (1 − покрытие)³ + CC`. Готового инструмента для Swift нет, по правилам «Build the Lever» сначала
считаю одну функцию вручную, потом пишу скрипт и кладу в `~/AI dev/ub-tools/`. jscpd и Muter запускаем только
на `Core`.

**Что проверяет пользователь после шага А:** ничего нового на экране не появляется. Один раз собираем
приложение, делаем одну картинку с эталонными настройками, она должна совпасть с эталоном.

## Шаг Б. Распутать `LilArtGen.swift:753` (сложность 72, 345 строк)

Это точка входа командной строки: один `main` разбирает режимы (`--sheet`, `--check-part`, `--import-part`,
`--squeeze`, обычная пачка картинок) и сам их выполняет.
1. Сначала фиксируем, что делает каждый режим: вывод `--help`, ошибки на неверных аргументах, разбор файла
   заданий (`loadJobs`), `parseSeed`, `parseSampler`, `variants`, `checkSize`. Всё это уже отдельные функции,
   их покрываем тестами.
2. Потом режем `main` на одну функцию на режим, а `main` оставляем диспетчером из нескольких строк.
3. Заодно: `ImportRunner.swift:785` (27) и `:127` (19), `ModelLibrary.swift:278` (20),
   `ScaledCheckpoint.swift:106` (23), `ControlNets.swift:129` (18). Конвертация моделей занимает часы, поэтому
   её страхуем тестами на маленьких искусственных файлах.

**Что проверяет пользователь после шага Б:** одна команда `tools/lilart-gen` на одну картинку (она займёт
минуту-две и память, поэтому сначала спрошу) и один импорт маленькой модели. Приложение в этом шаге почти
не меняется.

## Шаг В. Разрезать `Studio` и `ContentView`

Сначала механически, без смены логики, по одному куску за раз. Каждый кусок: вырезать, собрать, сравнить
с эталоном, закоммитить.
- `Studio.swift` → отдельные файлы расширений: очередь и запуск (`enqueue`, `drain`, `runImage`, `runVideo`),
  перевод и улучшение, выбор модели, правка (edit), видео, зоны. Движок-актор остаётся как есть.
  Некоторые `private` придётся ослабить до внутренних: это единственное изменение внутри кусков.
- `ContentView.swift` → по файлу на экран: боковая панель, холст правки, блок PRO, блок «ещё настройки»,
  боковая панель видео, галерея, окно моделей.
- Потом, когда куски лежат отдельно, решения переезжают в чистые функции с тестами: `makeImageJobs`,
  `makeEditJobs`, `makeVideoJob` превращаются в сборщик запроса, который проверяется без окна.

**Что проверяет пользователь после каждого куска Б→В (рукой, сам я экран не трогаю):**
| Кусок | Что нажать |
|---|---|
| Очередь и запуск | «Сгенерировать», потом ещё раз во время работы («добавить в очередь»), «отмена» |
| Перевод и улучшение | Написать по-русски, «перевести», «улучшить», «Сгенерировать» |
| Выбор модели | Переключить модель, перейти на вкладку «правка» и обратно, модель запомнилась |
| Правка | Загрузить фото, нарисовать маску, переключить «маска / рамки», запустить |
| Видео | Выбрать видеомодель, запустить короткий ролик |
| Боковая панель и PRO | Открыть PRO, поле Shift и размер, «ещё настройки», меню не упирается в край |

## Порядок и что нельзя пропускать

1. Эталонные картинки (нужна помощь пользователя: одна пара запусков, ему не придётся ничего считать).
2. Шаг А целиком, потом шаг Б, потом шаг В.
3. Каждый кусок — отдельный небольшой коммит с описанием: зачем, что изменилось, чем доказано.
4. Push, релиз и публикация только после слова «публикуем».

## Предупреждения о ресурсах

- Сборка приложения с движком: несколько минут и до 5 ГБ в `build/`, повторять придётся после каждого куска.
- Эталонные картинки и проверка генератора грузят GPU и память: перед запуском спрошу.
- Покрытие и Muter запускаем только на `Core`. Запуск на всём проекте и установка любых новых инструментов — по отдельному «да».
